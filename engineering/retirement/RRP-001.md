# RRP-001 — Repository Retirement Programme: policy and manifests

Status: **policy record issued under owner directive D11**. This is a documentation and
governance PR. It deletes nothing, contacts no provider, rewrites no Git history and does
not modify any approved document bytes.

Owner review baseline (FINAL3): Fieldbook `3c3279bdaa8df6aa44018184fefb662e98b5e0c1`,
Nirnay `f6842d2b6438c657c4d4eaec8edb3920193d2181`, Workspace `c9536c4`. The two local
clones were read-only sources for the manifests and were at exactly those heads.

## 1. Owner directive D11 — Retirement of Synthetic Market-Data Test Assets

The owner has explicitly directed that files which generate synthetic market-shaped tests
must go. **D11 supersedes the earlier W1.1 policy of preserving their source while
disabling execution.** The freeze is unchanged: synthetic market-shaped tests `DISABLED`
becomes *retired*, not *permitted*, and `test_data_policy` remains "strict prohibition
retained; versioned amendment not approved".

D11 requires removal from the active trees of:

- Synthetic market-data generators and fixture connectors.
- Fabricated instrument and listing records; invented corporate-action records.
- Synthetic market calendars; fake trades, quotes and depth; synthetic order-book sequences.
- Market-shaped golden files and mock exchange market-data sources.
- Synthetic strategy and portfolio results, including approval-looking artifacts.
- Benchmarks driven by invented market observations.
- Commands that regenerate or verify those assets.

Two protections are part of D11:

1. **Preserve W1.1 and W1.2 test-policy records.** Their reported counts are historical and
   remain unchanged. A new, dated test-retirement record is published by RRP-002; historical
   digests are not edited.
2. **Do not create replacement synthetic data.** Retaining `synthetic` as a provenance or
   rejection value is required so that old synthetic data can still be identified and
   rejected. A `TEST_ONLY` amendment would need a separate, versioned owner decision.

## 2. Six dispositions

Every candidate file in the two manifests has exactly one disposition. Age is not a
deletion criterion; a three-year-old protocol specification may be essential while a
two-day-old generator may be inappropriate.

| Disposition | Meaning |
|---|---|
| `DELETE` | Remove from the active repository (normal `git rm`; blob stays in history) |
| `ARCHIVE` | Preserve as historical evidence outside the active development tree |
| `DEPRECATE` | Freeze and remove after migration |
| `CONSOLIDATE` | Merge into one canonical document or implementation |
| `KEEP` | Retain as a required component |
| `CONDITIONAL` | Retain only if a documented dependency or use exists |

`ARCHIVE` and `DEPRECATE` are available for later PRs; no current row uses them because
the hashes in these manifests are themselves the dated retirement record outside the
active tree. `REPLACE` in the owner directive is recorded as `CONSOLIDATE`.

## 3. Per-file record schema

Both CSVs use the same 14 columns: the owner's 12 required fields plus `disposition` and
`priority`.

| Column | Meaning |
|---|---|
| `path` | Exact tracked path in the repository at the reviewed head |
| `repo` | `fieldbook` or `nirnay` |
| `current_commit` | Full 40-character reviewed head the path and hash were measured at |
| `sha256` | SHA-256 of the file bytes (`shasum -a 256`) |
| `size` | Byte size (`stat -f %z`) |
| `owner` | Accountable role from the 2026-11-23 owner ratification |
| `classification` | D11 candidate group, or the explicit protection group for `KEEP` rows |
| `disposition` | One of the six values in section 2 |
| `priority` | `P0`, `P1` or `P2` from section 4 |
| `reason` | Why this file is retired, consolidated or retained |
| `dependants` | Crosswalk targets that must be updated first |
| `replacement` | Canonical replacement, or "none" where D11 forbids one |
| `removal_condition` | The gate that must be satisfied before removal |
| `verification` | How the row was measured and re-checked |

## 6. Binding rules for the RRP sequence

1. **No history rewriting without a separate rights decision.** A normal `git rm` removes a
   file from the current tree and preserves the blob, commits and review evidence. Some
   old `measurements/live` directories may carry provider-origin data; if current rights do
   not permit retention or distribution, a separate data-rights decision must define a
   controlled purge with reissued bundles and invalidation of old packages. Do not rewrite
   history to make the repository smaller. A historical SHA-256 may remain as evidence
   where the applicable rights permit that record.
2. **No broad `git rm -r`.** Removal is per manifest row, after crosswalk review.
3. **Preserve W1.1/W1.2 historical records and digests.** Keep bootstrap pins separate from
   reviewed and tested heads; keep Fieldbook, Nirnay Python and Nirnay Rust counts tied to
   their own commits. Do not combine them into one headline number.
4. **Freeze Nirnay source-ingestion and raw-archive paths until replacements exist** and
   their NDC projections are accepted (RRP-004). Update ownership metadata and prohibit new
   features in those paths; delete nothing there under D11.
5. **Keep generic platform infrastructure.** Fieldbook `src/acquisition/{session,transport,
   egress,arbiter,supervisor,codec}.rs`, `src/integrity/{journal,replay}.rs` and
   `src/governance/` remain; Nirnay's pure numeric corpus and oracle code remain. Remove
   obsolete venue adapters and test data, not production engines, risk engines or decoders.
6. **Do not edit approved bytes casually.** NDC v2 requirements, the C0 model and the
   ownership ADR keep their digests. Registry/status corrections are documentation edits;
   a substantive contract change needs an approved new digest.
7. **One authority per responsibility.** The cleanup is not a file-count exercise: the goal
   is the fewest independent implementations, authoritative documents, unexplained
   dependencies and the clearest evidence chain.
8. **No provider contact, collection, experiment or live execution** is authorised by this
   programme. The freeze in `CURRENT-STATE.json` stays in force.
